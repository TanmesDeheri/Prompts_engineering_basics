## Task Tracker API — Architecture Scope

### 1. System Architecture Scope

The **Task Tracker API** will be a backend REST service for B2B organizations to manage users and tasks through authenticated API endpoints.

**In scope:**

* **API Layer:** RESTful HTTP endpoints for user and task operations.
* **Authentication & Authorization:** User signup, authentication, and role/resource-based access control.
* **User Management:** Create and manage user accounts within an organization.
* **Task Management:** Create, retrieve, update, and manage task status/details.
* **Validation:** Request validation, required-field checks, and business-rule enforcement.
* **Error Handling:** Consistent HTTP status codes and structured API error responses.
* **Security:** Password protection, authentication tokens, authorization checks, and input sanitization.
* **Auditability:** Track relevant task/user changes for business accountability.
* **Integration Boundary:** API should be consumable by web applications, mobile clients, or other B2B systems.

**Out of scope for now:**

* Database schema/design
* Backend implementation/code
* Frontend/UI
* Detailed infrastructure/deployment architecture
* Third-party integrations

## 2. Core B2B User Stories

### User Story 1 — User Signup

**As a business user,**
I want to create an account through the Task Tracker API,
so that I can securely access task-management functionality.

**Acceptance Criteria**

| ID    | Acceptance Criterion                                                                                                                         |
| ----- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| US-01 | Given valid required user information, when a signup request is submitted, then the API creates the user account successfully.               |
| US-02 | The API must reject signup when a required field is missing or invalid.                                                                      |
| US-03 | The API must prevent registration using an email address that already belongs to an existing account.                                        |
| US-04 | The user's password must not be stored or returned in plaintext.                                                                             |
| US-05 | A successful signup returns an appropriate success HTTP status and user-related response information without exposing sensitive credentials. |
| US-06 | Invalid requests return a consistent error response explaining the validation failure.                                                       |

---

### User Story 2 — Task Creation

**As an authenticated business user,**
I want to create a task through the API,
so that work can be assigned and tracked within my organization.

**Acceptance Criteria**

| ID    | Acceptance Criterion                                                                                              |
| ----- | ----------------------------------------------------------------------------------------------------------------- |
| US-07 | Given a valid authenticated request, when task details are submitted, then the API creates the task successfully. |
| US-08 | The API must validate required task information before creation.                                                  |
| US-09 | A task must have a unique identifier generated by the system.                                                     |
| US-10 | The task must be associated with the authenticated user's organization/context.                                   |
| US-11 | Unauthorized or unauthenticated requests must not be allowed to create tasks.                                     |
| US-12 | A successful creation returns the appropriate HTTP status and the created task representation.                    |

---

### User Story 3 — Task Updates

**As an authenticated business user with appropriate permissions,**
I want to update an existing task,
so that its details and progress remain accurate.

**Acceptance Criteria**

| ID    | Acceptance Criterion                                                                                                   |
| ----- | ---------------------------------------------------------------------------------------------------------------------- |
| US-13 | Given a valid task identifier and authorized user, when valid update data is submitted, then the API updates the task. |
| US-14 | The API must reject updates containing invalid or unsupported field values.                                            |
| US-15 | A request for a non-existent task must return an appropriate not-found response.                                       |
| US-16 | A user without sufficient permissions must not be able to update the task.                                             |
| US-17 | Successful updates return the updated task representation and appropriate HTTP status.                                 |
| US-18 | Relevant task changes should be auditable, including who made the change and when.                                     |


## SQL Schema Design
CREATE TABLE users (
    id BIGINT PRIMARY KEY,
    name VARCHAR(255) NOT NULL,
    email VARCHAR(255) NOT NULL UNIQUE,
    password_hash VARCHAR(255) NOT NULL,
    created_at TIMESTAMP NOT NULL
);

CREATE TABLE tasks (
    id BIGINT PRIMARY KEY,
    user_id BIGINT NOT NULL,
    title VARCHAR(255) NOT NULL,
    description TEXT,
    status VARCHAR(50) NOT NULL,
    due_date DATE,
    created_at TIMESTAMP NOT NULL,

    CONSTRAINT fk_tasks_user
        FOREIGN KEY (user_id)
        REFERENCES users(id)
);

## Controller Code
For the junior QA/developer team, I’ll use **Node.js + Express with PostgreSQL-style parameterized raw SQL**. Parameterized queries prevent user input from being concatenated directly into SQL, while keeping the controller logic separated from database access.

```javascript
// controllers/taskController.js

// Assumes a PostgreSQL connection pool exported from db.js.
// Example: const pool = new Pool({ connectionString: process.env.DATABASE_URL });
const pool = require("../db");

/**
 * POST /api/v1/tasks
 * Create a new task.
 */
const createTask = async (req, res) => {
    try {
        // Express parses the JSON request body into req.body.
        // We destructure only the parameters required by this endpoint.
        const { title, description, due_date } = req.body;

        // Validate required input before accessing the database.
        if (!title || typeof title !== "string" || title.trim() === "") {
            return res.status(400).json({
                error: "Title is required"
            });
        }

        // For this example, the authenticated user's ID is expected
        // to be attached to req.user by authentication middleware.
        const userId = req.user?.id;

        if (!userId) {
            return res.status(401).json({
                error: "Authentication required"
            });
        }

        // Parameterized SQL values ($1, $2, ...) prevent SQL injection.
        // status has a default business value of 'pending'.
        const sql = `
            INSERT INTO tasks (
                user_id,
                title,
                description,
                status,
                due_date,
                created_at
            )
            VALUES ($1, $2, $3, $4, $5, CURRENT_TIMESTAMP)
            RETURNING id, user_id, title, description, status, due_date, created_at
        `;

        const values = [
            userId,
            title.trim(),
            description ?? null,
            "pending",
            due_date ?? null
        ];

        const result = await pool.query(sql, values);

        return res.status(201).json({
            data: result.rows[0]
        });

    } catch (error) {
        console.error("Create task error:", error);

        return res.status(500).json({
            error: "Internal server error"
        });
    }
};


/**
 * GET /api/v1/tasks/:id
 * Retrieve a specific task by ID.
 */
const getTaskById = async (req, res) => {
    try {
        // Express parses the dynamic URL parameter
        // /api/v1/tasks/:id and makes it available as req.params.id.
        const taskId = req.params.id;

        // Validate that the ID is a positive integer before querying.
        if (!/^\d+$/.test(taskId) || Number(taskId) <= 0) {
            return res.status(400).json({
                error: "Invalid task ID"
            });
        }

        const userId = req.user?.id;

        if (!userId) {
            return res.status(401).json({
                error: "Authentication required"
            });
        }

        // $1 and $2 are PostgreSQL query parameters.
        // The values are supplied separately rather than concatenated
        // into the SQL string.
        const sql = `
            SELECT
                id,
                user_id,
                title,
                description,
                status,
                due_date,
                created_at
            FROM tasks
            WHERE id = $1
              AND user_id = $2
        `;

        const values = [Number(taskId), userId];

        const result = await pool.query(sql, values);

        if (result.rows.length === 0) {
            return res.status(404).json({
                error: "Task not found"
            });
        }

        return res.status(200).json({
            data: result.rows[0]
        });

    } catch (error) {
        console.error("Get task error:", error);

        return res.status(500).json({
            error: "Internal server error"
        });
    }
};


module.exports = {
    createTask,
    getTaskById
};
```

### Design notes for QA

| Area                                  | Expected behavior                      |
| ------------------------------------- | -------------------------------------- |
| Create task                           | `201 Created`                          |
| Missing title                         | `400 Bad Request`                      |
| Missing authentication                | `401 Unauthorized`                     |
| Invalid task ID                       | `400 Bad Request`                      |
| Task doesn't exist / isn't accessible | `404 Not Found`                        |
| Successful GET                        | `200 OK`                               |
| Database/server failure               | `500 Internal Server Error`            |
| SQL injection protection              | Parameterized `$1`, `$2`, etc.         |
| User isolation                        | Queries restrict tasks using `user_id` |

The `user_id` restriction in the `GET` query is intentional: it prevents an authenticated user from retrieving another user's task merely by changing the task ID.
